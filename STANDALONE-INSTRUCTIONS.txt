FREEPBX CARE - STANDALONE SERVER INSTRUCTIONS
Prepared: 2026-10-23 | Script: 2026.10.23-asterisk-smtp-r3

Run every command directly ON THE PBX SERVER as root, over SSH or its console.
This tool configures monitoring and outgoing email for an existing FreePBX
installation. It does not install Debian, FreePBX or extensions.

1. BEFORE STARTING
==================
Supported platform: FreePBX 17 on Debian 12, with systemd and Python 3.
Have a current, recoverable PBX backup and the SMTP mailbox password from the
company's secure credential store. Confirm the correct customer/server.
Use an approved maintenance window for migration or outgoing-email changes.
Postfix SMTP changes also affect other outgoing mail, including voicemail.

Become root if necessary:
  sudo -i

Check the platform and clock:
  cat /etc/os-release
  fwconsole --version
  command -v python3
  timedatectl status

If the platform differs, Python is missing, or the clock is wrong, have the
administrator resolve that first. Do not bypass platform checks. Working DNS
and access to GitHub and the SMTP relay are required.

Choose the correct path:
  NEW server, no legacy monitors: section 2, then section 4.
  OLD server with legacy monitors: sections 2 and 3, then section 4.
  Existing working FreePBX Care installation: section 7; no legacy cleanup.
  Only changing email settings: section 5, then section 6; no cleanup needed.

3. OLD SERVERS: CLEAN UP BEFORE INSTALLING THE REPLACEMENT
=======================================================
Skip this section for a new server with no legacy monitors.

A. NORMAL MIGRATION: KEEP EXISTING SMTP DURING CLEANUP

First preview; this does not apply cleanup:
  bash /root/cleanup-legacy-freepbx.sh

Review the listed files and cron jobs. Then apply:
  bash /root/cleanup-legacy-freepbx.sh --apply

Wait for 'Cleanup complete' or 'No legacy changes needed'. For errors, use
section 8; do not proceed as if cleanup succeeded.

The cleaner removes recognized root cron entries and archives these monitors:
  /usr/local/bin/asterisk-monitor.sh
  /usr/local/bin/extension_monitor.sh

It archives exact recognized installer copies, preserves modified/unknown
installers, and disables a recognized existing FreePBX Care timer. It does not
restart Asterisk. SMTP settings and sender rewrites stay by default.
Backups, including root crontab and relevant Postfix files, are under:
  /var/lib/freepbx-care/legacy-backup-TIMESTAMP/

Other users' cron jobs, custom paths and schedulers need administrator review.
Do not clear the entire crontab. Rejected chained commands must be reviewed
and separated from unrelated tasks by the administrator.
Continue promptly to section 4 because legacy monitoring is now disabled.

B. OPTIONAL: RESET OLD SMTP SETTINGS TOO

Use only when deliberately replacing the old relay settings and prepared to
complete new SMTP setup immediately. This is not required for normal migration.
Use this path instead of A when a reset is planned:
  bash /root/cleanup-legacy-freepbx.sh --reset-smtp
  bash /root/cleanup-legacy-freepbx.sh --apply --reset-smtp

A recognized reset archives old relay password files, detaches recognized old
sender rules, and defers smtp/relay delivery until current SMTP setup completes.
Queued messages are retained subject to normal queue expiry. Unknown/custom
relay configurations are not automatically reset; read the reported plan.
Continue section 4 INCLUDING option 3. Do not remove the reset marker manually,
bypass mail deferral, or delete/flush the queue to fix a pending reset.

The separate --remove-sender-rewrites flag is for an administrator deliberately
changing recognized old sender rules. It can change voicemail sender identity;
it is not part of routine cleanup.

4. SETUP FOR NEW OR CLEANED OLD SERVERS
=====================================
Open the menu:
  bash /root/freepbx-care.sh

Menu options:
  1 Configure Asterisk monitor
  2 Install/update monitoring
  3 Configure SMTP relay
  4 Read-only health/status
  5 Send test email
  6 Pause monitoring
  7 Resume monitoring
  8 Disable monitoring
  9 Collect diagnostics (no restart)
  0 Exit

Recommended order: 1 -> 3 -> 5 -> 4 -> 2 -> 0.
Wait for actual test-email receipt before enabling monitoring with option 2.
If intentionally keeping already verified SMTP on an old server, skip option 3
but still do option 5 and confirm receipt. After an SMTP reset, option 3 is
mandatory.

OPTION 1 - CONFIGURE ASTERISK MONITOR

Enter these company production values. Type each explicitly if the displayed
default differs:

  Alert recipient:
    monitor@famecomputers.com
  Sender email (blank keeps system default):
    support@famepbx.com
  Enable automatic recovery? y/n:
    y
  Defer restart while CLI reports active channels? y/n:
    y
  Consecutive failed checks:
    3
  Restart cooldown seconds:
    1800
  Maximum restart attempts per hour:
    2
  AMI settings: auto or manual?:
    auto

For an observation-only pilot choose n for automatic recovery. Alerts and
health monitoring still work; change it to y with option 1 after validation.
Change sender/recipient only if approved for this server/customer.

AMI 'auto' reads this server's own local FreePBX credentials. It is separate
from SMTP: never use the email password as an AMI secret. If auto fails, collect
status and ask the administrator instead of guessing manual credentials.

OPTION 3 - CONFIGURE SMTP
Use the exact answers in section 5.

OPTION 5 - SEND TEST EMAIL
'Accepted by local sendmail' means accepted into the local queue only. Confirm
receipt at monitor@famecomputers.com. If missing, follow section 6.

OPTION 4 - READ HEALTH/STATUS
Expect CLI true, AMI healthy and healthy true. A healthy result may show
restartable false: a healthy Asterisk does not need recovery. Fix CLI/AMI errors
before installing monitoring. Check for unintended pauses too.

OPTION 2 - INSTALL/UPDATE MONITORING
Installs and enables the systemd timer. Configuration alone does not schedule
checks. Resolve installation errors before handoff. Installation does not
restart Asterisk, but enabled automatic monitoring may recover it later.

OPTION 0 - EXIT, THEN VERIFY
  systemctl is-enabled freepbx-care.timer
  systemctl is-active freepbx-care.timer
  systemctl list-timers --all freepbx-care.timer
  bash /root/freepbx-care.sh status

Expected timer results: enabled and active. The oneshot service may be inactive
between checks; inspect its journal for actual failures:
  journalctl -u freepbx-care.service -n 50 --no-pager

Test normal incoming/outgoing calls and a voicemail email. Record hostname,
script version, health, timer status, test-mail receipt, voicemail result and
whether automatic recovery is enabled. Never record passwords.

5. SMTP PROMPT ANSWERS
=====================
Choose menu option 3, or run directly:
  bash /root/freepbx-care.sh smtp

For the current company support@famepbx.com relay, enter:

  SMTP relay DNS hostname (must match its certificate):
    premium117-1.web-hosting.com
  SMTP port [587]:
    465
  TLS mode: starttls or implicit (465) [implicit]:
    implicit
  SMTP username:
    support@famepbx.com
  SMTP password:
    Actual mailbox/app password from the secure credential store.
    Input is hidden; this is normal. Do not put it in a shell command.
  Monitor sender email:
    support@famepbx.com

These settings were verified for this mailbox. If the provider migrates the
account, use its updated SMTP hostname and matching updated instructions.
The email domain alone does not determine the relay hostname.

Do NOT use 162.0.229.110 at the hostname prompt: it produced a certificate
'IP address mismatch'. Keep certificate verification enabled and use the DNS
hostname above. The older SMTP installer could deliver using an IP because
its TLS settings did not require the same certificate identity checks.

For another approved provider use its documented SMTP hostname, credentials
and port. Port 587 normally uses starttls; port 465 normally uses implicit.
Do not reuse this account's settings for another provider.

Setup may install missing mail packages and restarts Postfix, not Asterisk.
Relevant backups: /var/lib/freepbx-care/smtp-backup-TIMESTAMP/.
Unrelated Postfix configuration is preserved; existing sender rewriting can
still affect voicemail. Test actual delivery and sender identity after changes.

6. VERIFY EMAIL DELIVERY
=======================
  bash /root/freepbx-care.sh test-mail
  postqueue -p
  tail -n 60 /var/log/mail.log

Match the new message's time and queue ID. 'status=sent' with a successful
relay response means relay acceptance; confirm the recipient's inbox/spam
folder too. An empty queue alone does not prove inbox delivery.
If mail.log is unavailable, try:
  journalctl --since "15 minutes ago" --no-pager | grep -i postfix

Certificate error / IP mismatch: rerun section 5 using the DNS hostname.
Old errors remain in logs, so compare timestamps with your new attempt.
Authentication failure / 535: verify the mailbox/app password with the account
administrator and rerun SMTP setup. Never print/share the password map.
Connection timeout/refused: administrator checks DNS, outbound port 465 and
provider availability from this PBX.
Deferred after intentional reset: finish option 3 using the current main script;
do not manually remove /etc/freepbx-care/smtp-reset.json.

After fixing the cause, retry a specific queued message:
  postqueue -i QUEUE_ID
Replace QUEUE_ID with the actual ID from postqueue -p, then recheck logs and
receipt. Do not type the placeholder literally or delete the queue.

7. ROUTINE OPERATION, MAINTENANCE AND UPDATES
===========================================
Status and diagnostics without deliberately requesting recovery:
  bash /root/freepbx-care.sh status
  bash /root/freepbx-care.sh diagnose
Diagnostics go under /var/log/freepbx-care/ and may contain sensitive call
metadata. The 'check' command can trigger recovery; it is not a read-only test.

Before intentionally stopping/restarting Asterisk, restoring, backing up or
performing disruptive maintenance, pause for enough time:
  bash /root/freepbx-care.sh pause --minutes 120
Adjust 120 to the planned duration and extend if work overruns. Pauses expire
automatically and also suppress monitoring/alerts. Wait for an existing check
or recovery to finish before disruptive work.

After maintenance, check Asterisk is healthy, then:
  bash /root/freepbx-care.sh resume
  bash /root/freepbx-care.sh status

A separate backup pause remains independent of manual resume. Only after the
backup finishes, if status shows such a pause, use:
  bash /root/freepbx-care.sh backup-resume
This leaves a three-minute settling period. Do not clear an active backup's pause.

Disable future scheduled checks:
  bash /root/freepbx-care.sh disable
This does not cancel a recovery already running. Enable again with:
  bash /root/freepbx-care.sh install

Change recipient/recovery settings: menu option 1.
Change SMTP: option 3, then option 5 and confirm receipt.
Saved settings apply to later checks; no legacy cleanup is needed.

UPDATE AN EXISTING WORKING FREEPBX CARE INSTALLATION
Update and verify one server first. Keep its settings. Back up the current script:
  cp -p /root/freepbx-care.sh /root/freepbx-care.before-update-$(date +%Y%m%d-%H%M%S).sh
Pause as above, then download/replace ONLY the main script using section 2.
  bash /root/freepbx-care.sh --version
  bash /root/freepbx-care.sh preflight
  bash /root/freepbx-care.sh install
  bash /root/freepbx-care.sh test-mail
Confirm receipt and healthy status, resume, and verify the timer as in section 4.
An existing pause remains until expiry or resume. Do not rerun cleanup or SMTP
just to update the script. If any step fails, stop and obtain administrator
review before resuming. Keep the previous script for reviewed rollback.

8. MIGRATION AND INSTALLATION TROUBLESHOOTING
===========================================
A. 'A monitor/recovery is running; wait for it to finish and retry'
Inspect without stopping Asterisk:
  lslocks -o PID,COMMAND,PATH
  fuser -v /tmp/ast_mon.lock /run/freepbx-care.lock
  tail -n 12 /var/log/asterisk_monitor.log
Wait for a real monitor, fwconsole or recovery operation to finish. Do not kill
safe_asterisk/asterisk or delete the lock to force cleanup.

Some old monitors left /tmp/ast_mon.lock inherited by running Asterisk daemons.
When safe_asterisk/asterisk are its ONLY holders and the Asterisk CLI responds,
the current cleaner provides a guarded migration:
  bash /root/cleanup-legacy-freepbx.sh --apply --retire-inherited-lock
It verifies holders/readiness, backs up and disables recognized legacy cron,
retires the old lock and cleans up without signalling Asterisk. It refuses
other holders or uncertain conditions. If refused, collect the error and ask
the administrator. This does not retire /run/freepbx-care.lock.
Backups: /var/lib/freepbx-care/lock-retirement-TIMESTAMP/.
If retirement fails after disabling old cron, jobs deliberately remain disabled
to prevent a race. Finish migration promptly with administrator help. After
success, continue section 4.

B. 'Legacy monitor jobs remain'
Run section 3 preview/apply. Do not rerun the old installer or bypass the guard.
Custom or chained jobs need administrator review.

C. Unsupported platform or Debian repository errors
Confirm Debian 12 / FreePBX 17 and the current script. If apt reports stable
changing to trixie, or the script flags moving suites, stop for repository
review. Debian 12 needs appropriate bookworm suites. Do not blindly accept a
release change, upgrade Debian, or replace every 'stable' string: third-party
repositories can legitimately use different suite names.

D. CLI unhealthy, AMI config_error/auth_error or preflight failed
  bash /root/freepbx-care.sh status
  bash /root/freepbx-care.sh diagnose
  systemctl status mariadb --no-pager
Have the administrator fix the local AMI/FreePBX/database issue before enabling
automatic recovery. Do not publish /etc/freepbx.conf, guess credentials, use
the SMTP password for AMI, or expose AMI port 5038 to the Internet.

E. Recovery timeout / recovery_blocked
Further automatic attempts are blocked after a recovery timeout. Review
diagnostics and /var/log/freepbx-care/last-restart.log. The administrator must
check any remaining fwconsole operation and the PBX's actual condition first.
Only after review, 'resume' clears the timeout latch. Do not repeatedly resume
to force retries or run fwconsole restart while calls may be active.

F. Cleanup or SMTP failed partway through
Read the complete error and backup path. Rollback is attempted; do not assume
everything was restored. The Care timer may remain disabled after failed
cleanup. Verify health, mail and timer state, then resolve the failure and
finish setup. Preserve backups. Do not restore all old cron blindly and create
competing monitors.

9. MONITOR BEHAVIOR AND HANDOFF NOTES
===================================
The timer starts five minutes after boot, then schedules checks about 60 seconds
after the previous check finishes, plus up to 15 seconds of randomized delay.
Long checks, cooldowns and settling periods delay recovery; three failures do
not guarantee a restart in three minutes.

Standard settings: three consecutive failed checks, 30-minute cooldown, maximum
two recovery attempts per hour. CLI and AMI are evaluated together. AMI
authentication/configuration errors alone do not force a restart of an otherwise
responsive Asterisk. Active-channel deferral helps when CLI responds; it cannot
guarantee call preservation when CLI is unresponsive. Recovery can interrupt
calls and does not fix the underlying cause of repeated crashes/timeouts.

There is no extension registration polling. Use external monitoring to detect
a powered-off or unreachable whole server.

Operational files (keep credentials and diagnostics private):
  /root/freepbx-care.sh                  Administrator script
  /etc/freepbx-care/config.json          Settings; may contain secrets
  /etc/postfix/freepbx-care-sasl          SMTP credentials, plus its .db file
  /var/lib/freepbx-care/                 State, pauses and setup backups
  /var/log/freepbx-care/                 Diagnostics and recovery output
