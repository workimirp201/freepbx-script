FreePBX Care 2026.10.23-asterisk-smtp
==================================

UPDATE: For cleanup initiated from the Proxmox HOST, including an explicit SMTP
reset, see PROXMOX-CLEANUP.txt. Its procedure supersedes the default-preserve
cleanup instructions below when --reset-smtp is selected. Use main script r2.

SCOPE

This version contains Asterisk CLI/AMI monitoring and Postfix SMTP setup only.
Extension polling is removed, including when old properties settings exist.
Target: FreePBX 17 on Debian 12, including Proxmox LXC with working systemd.
No live containers or Proxmox hosts were accessed or modified during development.

Files:
  cleanup-legacy-freepbx.sh       Standalone cleanup; preview unless --apply
  freepbx-care.sh                Rerunnable Asterisk/SMTP administrator
  monitor-config.example.json    Shared settings; auto_restart=false for pilot
  smtp-profile.example.json      Shared SMTP template; replace placeholders
  proxmox-freepbx-backup-hook.sh  OPTIONAL host hook; not installed automatically
  test_*.py                     Local tests
  upstream/                     Reviewed originals; do not execute again

The main and cleanup .sh tools launch embedded Python 3 standard-library code.
Run them with bash. No pip packages. The optional host hook is ordinary Bash.

TWO-PHASE DEPLOYMENT: INSIDE EACH FREEPBX CONTAINER

Copy the cleanup and main scripts into /root. First preview:
  sudo bash /root/cleanup-legacy-freepbx.sh

Then apply cleanup:
  sudo bash /root/cleanup-legacy-freepbx.sh --apply

Start the new administrator:
  sudo bash /root/freepbx-care.sh

Menu order: 1 configure monitor, 3 configure SMTP if needed, 5 test mail,
4 inspect health, 2 install/update monitoring, 0 exit. For the initial pilot,
answer n to automatic recovery. Confirm test mail actually arrives.

Rerun the same main command to change settings. Configuration takes effect on
the next check. Updating service/timer definitions requires option 2 again.
Installation does not restart Asterisk. SMTP setup restarts Postfix. The idle
menu does not hold the monitor lock; individual operations do.

Complete replacement promptly after cleanup because old monitoring is disabled.
There is no public curl URL for this new bundle; transfer the supplied files.

CLEANUP: WHAT IT DOES

1. Backs up root's current crontab and relevant existing Postfix/aliases files
   under /var/lib/freepbx-care/legacy-backup-TIMESTAMP, with restricted access.
2. Removes active root cron jobs for the exact old runtime paths:
     /usr/local/bin/asterisk-monitor.sh
     /usr/local/bin/extension_monitor.sh
   It preserves comments and similar filenames, and refuses chained commands
   rather than silently removing another task on the same line.
3. Archives those runtime scripts. Archives known /root installer copies only
   when their content hashes match the reviewed originals. Modified/unknown
   installers are reported and preserved; other names/locations are not guessed.
4. Disables a recognized previous FreePBX Care timer if enabled/active, keeping
   its settings and state for the replacement. A running recovery blocks cleanup.
5. Refuses active legacy monitor processes/locks. It does not kill recovery.
6. On failure, attempts file/crontab/Postfix rollback. A timer it disabled remains
   disabled; inspect the reported backup and explicitly reinstall when ready.

Repeated cleanup is safe when these artifacts are already absent. Cleanup does
not remove packages, firewall settings, Incron, PM2, Asterisk configuration,
working SMTP credentials, queues, aliases, original logs or old backups. Unknown
/tmp property flags are harmless once scheduling is gone; no wildcard deletion.
It does not guess at custom cron.d jobs, other users' jobs or other watchdogs.

The original SMTP installer overwrote main.cf. Its prior contents cannot be
reconstructed without a known-good backup; cleanup does not choose one blindly.
Existing working mail routing is preserved by default, including sender maps.

OPTIONAL removal of exact old sender-rewrite references:
  bash /root/cleanup-legacy-freepbx.sh --remove-sender-rewrites
  bash /root/cleanup-legacy-freepbx.sh --apply --remove-sender-rewrites

This detaches recognized generic/canonical/header map references only, validates
and reloads Postfix. It preserves custom maps and leaves map files for rollback.
Removing these rules can change voicemail/user sender identities and relay
acceptance. Keep default preservation until those mail paths have been tested.

SHARED SETTINGS FOR 90+ LXC CONTAINERS

Edit the JSON examples. Use unique container hostnames and maintain a mapping
of Proxmox node, CTID and hostname; alert subjects contain the hostname. Keep
ami={} to detect each container's own FreePBX AMI credentials independently.
Do not distribute one container's AMI password to all the others.

After copying edited profiles to /root as root, an unattended setup is possible:
  install -d -m 700 /etc/freepbx-care
  install -m 600 /root/monitor-config.json /etc/freepbx-care/config.json
  chmod 600 /root/smtp-profile.json
  bash /root/freepbx-care.sh smtp --smtp-config /root/smtp-profile.json
  bash /root/freepbx-care.sh test-mail
  bash /root/freepbx-care.sh install

SMTP profiles must be root-owned regular files with permissions 600. Actual
passwords are read from the profile, not command-line arguments or shell history.
Use existing secret-management tooling for distribution. Never include real
profiles in Git, this distributable bundle or a public download. The example
password is deliberately rejected until changed.

Verify the same bundle on each target:
  sha256sum -c SHA256SUMS
  bash /root/freepbx-care.sh --version

MONITOR DECISIONS

- Health requires meaningful CLI uptime output and authenticated AMI Ping.
  FreePBX bootstrap skips its own AMI connection, then credentials are tested
  separately. Only loopback AMI is supported; no public AMI port is opened.
- Timer starts five minutes after container boot. Checks run 60 seconds after
  completion of the preceding check, plus up to 15 seconds of stable per-machine
  delay. Cloned machine IDs must be unique. Slow checks lengthen the interval.
- Three consecutive failures qualify an outage. CLI failure or unreachable AMI
  permits recovery; AMI authentication/configuration/protocol errors alone do not.
- CLI down + no Asterisk process: fwconsole start. Otherwise: fwconsole restart.
  Unknown process state defers recovery. Starting a missing process avoids the
  shutdown hooks that failed in your supplied log.
- When CLI works, active channels or unknown channel count defer recovery.
  When CLI is unresponsive, call activity cannot be assessed; recovery can
  interrupt calls. It skips visible concurrent fwconsole operations, though
  there is no global lock shared with every manual/external command.
- Defaults: at most two attempts per rolling hour, at least 30 minutes apart.
  Attempt state is saved BEFORE execution. Diagnostics are saved before recovery
  and again on failure. A later healthy check sends the recovery notification.
- Ten-minute command limit; timeout retains partial output and terminates the
  parent without killing Asterisk/PM2 daemons it may have launched. It latches
  further automatic recovery OFF for operator review. After checking processes,
  services and logs, clear the latch with: bash /root/freepbx-care.sh resume
- The watchdog uses KillMode=process specifically to let fwconsole-launched
  daemons outlive this oneshot check. This is a deliberate lifecycle tradeoff,
  not a general service recommendation. Timed-out descendants may remain alive;
  inspect them before clearing the latch. Outer service limit: fifteen minutes.
- A scheduling gap longer than five minutes resets failure counts and adds a
  three-minute settling period. This accommodates pauses/overload; it does not
  prove vzdump caused the gap. Smaller stalls still need consecutive failures.

Manual maintenance:
  bash /root/freepbx-care.sh pause --minutes 120
  # perform maintenance
  bash /root/freepbx-care.sh resume

Pause BEFORE stopping FreePBX. Disabling the timer prevents future checks but
does not cancel an existing recovery. Manual and backup pauses are independent.

LXC AND VZDUMP: BEFORE FINALIZING THE ROLLOUT

Proxmox documents container stop mode as downtime for the backup, suspend mode
as a copy followed by suspension during synchronization, and snapshot mode as
suspension while a temporary storage snapshot is created. Snapshot mode needs
snapshot-capable backed-up volumes. It does not guarantee uninterrupted calls.
Compare actual backup task mode/timestamps with outage timestamps by CTID/node.

Your log proves recovery failed: Incron did not process a firewall hook, several
PM2 commands timed out, and Asterisk readiness checks failed. It does not prove
that vzdump caused those errors. Check host storage latency, CPU/memory pressure
and OOM events during backup, and each container's memory/swap limits and cgroup
memory.events. LXC shares the host kernel; guest kernel logs can be incomplete
or unavailable. VM ballooning/QEMU guest-agent advice does not apply to LXC.

Stagger backup jobs and test bandwidth/compression limits against the storage
and live call load. Do not start recovery or package updates across all containers
simultaneously. Test restoring a representative FreePBX backup and database.

OPTIONAL BACKUP HOOK: HOST SIDE, NOT INSTALLED

The supplied hook runs on the Proxmox host and uses pct exec for allowlisted
running LXC containers. backup-start sets a separate 24-hour-expiring backup
pause. backup-end/abort reduces that pause to three minutes of settling. It
does not stop/restart Asterisk or clear a manual pause/recovery-timeout latch.
Increase the expiry if backups can last longer than 24 hours.

Host pilot preparation:
  install -m 700 proxmox-freepbx-backup-hook.sh /usr/local/sbin/freepbx-backup-hook.sh
  # Create /etc/freepbx-care-backup-ctids: one opted-in numeric CTID per line.
  # Install the main script inside those containers first.
  # Add --script /usr/local/sbin/freepbx-backup-hook.sh to the PILOT backup job.

Do not overwrite an existing vzdump hook. The script option selects one script;
existing behavior must be integrated. Review the installed Proxmox example at
/usr/share/doc/pve-manager/examples/vzdump-hook-script.pl. A failed pause/resume
command returns an error, which can fail/warn the backup task and needs attention.
Stopped CTs are skipped. Test successful and aborted backup paths before rollout.

SMTP

Supports STARTTLS (usually 587) or implicit TLS (usually 465), with certificate
verification against the relay hostname. Use its certificate DNS name. It stores
the Postfix password map/database as root-only files. It installs only missing
required packages and does not perform a general upgrade on each rerun.

Changes are limited to outbound relay/authentication/TLS parameters but affect
ALL outbound Postfix mail. Unrelated settings, sender maps, aliases and queues
are preserved. Apply failures attempt file rollback and a Postfix restart;
package side effects are not rolled back. Existing TLS/transport/master.cf rules
can affect delivery. Test actual mail and voicemail; local queue acceptance is
not delivery confirmation. Shared-account sender permissions/rate limits must
accommodate 90+ containers. This wizard uses passwords, not OAuth authentication.

CURRENT UPDATE GUIDANCE

Current Sangoma guidance for FreePBX 17 targets Debian 12/bookworm. Do not blindly
move to Debian 13/trixie or moving 'stable' repositories. OS package updates and
FreePBX module updates are separate tasks; plan and pilot both. This tool cannot
certify installed versions as current without inspecting each container.

Inventory inside each CT:
  cat /etc/os-release
  fwconsole --version
  asterisk -V
  dpkg-query -W postfix libsasl2-modules ca-certificates systemd incron
  fwconsole ma list
  apt list --upgradable  # depends on freshness of downloaded apt indexes

Review repositories before apt update/upgrade. Updates may require restarts and
interrupt calls. No bulk package/module upgrade is performed by this bundle.

PILOT ACCEPTANCE

1. Start with one noncritical CT, auto_restart=false. Apply cleanup and verify
   unrelated cron tasks, mail and voicemail sender/delivery behavior.
2. Verify CLI/AMI health and timer checks. Run a representative vzdump backup.
   If using the hook, test backup-start, end and abort behavior.
3. In a test CT with no calls, enable recovery and test stopped-Asterisk start
   and a fault requiring restart. Confirm Asterisk stays running AFTER the
   watchdog exits and through subsequent checks. Verify pause/latch handling.
4. Expand to a small batch on different hosts, then the remaining inventory.

Use an external monitor on an independent system for host/container availability
and missed-check heartbeats. A local watchdog/email cannot reliably report a
dead host, frozen CT, failed network or failed local mail system. This bundle
provides local state/journals for collection, not a central dashboard/orchestrator.

OPERATIONS / EVIDENCE

  bash /root/freepbx-care.sh status
  bash /root/freepbx-care.sh diagnose
  journalctl -u freepbx-care.service -n 100 --no-pager
  systemctl list-timers freepbx-care.timer
  postqueue -p
  tail -n 100 /var/log/mail.log  # if rsyslog/mail.log is configured

Settings: /etc/freepbx-care/config.json
State/pauses/backups: /var/lib/freepbx-care/
Evidence: /var/log/freepbx-care/incident-*.log (latest twenty retained)
Latest attempt: /var/log/freepbx-care/last-restart.log
Units: /etc/systemd/system/freepbx-care.service and .timer
Old log preserved: /var/log/asterisk_monitor.log

Snapshots include CLI/AMI health, relevant service status/journals, Asterisk full
tail, process states, available cgroup memory/CPU counters, disk/memory and kernel
messages. They are root-restricted because diagnostics may contain call metadata.
Missing/inaccessible LXC files are recorded without aborting all collection.
Do not publish unredacted credentials, profiles, backups or diagnostics.
